# Roadmap

This page lists what is planned for jScratch, roughly in the order it will happen. It is a plan, not a promise: priorities move when real projects turn up problems. [Supported blocks](blocks.md) is always the source of truth for what works today.

## Done: the MVP

- [x] `.sb3` parsing and validation with the official scratch-parser, on the JVM and in the browser
- [x] ASM code generation with typed expressions, custom blocks and "run without screen refresh"
- [x] Virtual-thread scheduler that follows scratch-vm's frame and yield rules
- [x] Java2D rendering with vector costumes, the pen layer and say bubbles
- [x] Broadcasts, clones, lists, `sensing_of` and ask and wait
- [x] WAV playback
- [x] MP3 and ADPCM WAV sounds, decoded by dr_mp3 and dr_wav compiled to JVM bytecode
- [x] Headless mode and screenshots for automated tests
- [x] TeaVM playground and the documentation site on GitHub Pages

## Next: close the compatibility gaps

These are the gaps most likely to break a project downloaded from the Scratch website, so they come first.

- [x] Pixel-accurate collision from costume alpha masks, honoring rotation and size
- [x] **Color sensing.** `touching color` and `color is touching color`, sampled from the costumes, the pen layer and the backdrop the way scratch-render's CPU path does.
- [x] **Graphic effects.** Color, brightness, fisheye, whirl, pixelate and mosaic, applied per sprite in the renderer the way scratch-render does.
- [x] **Monitors.** Draw variable and list monitors, and make the show and hide blocks control them. Monitors go into the frame snapshot as data, like sprites, instead of being Swing components in the window, so the [pluggable renderers](#then-performance-and-robustness) below can draw them too.
- [x] **Sound effects.** Pitch and pan, plus clear sound effects.
- [x] **Remaining hats.** `when timer greater than` first, since it needs no microphone. Loudness follows if microphone input proves workable through `javax.sound.sampled`.
- [x] **Small sensing blocks.** Drag mode for draggable sprites, and a `username` that can be set with a system property.

## Then: performance and robustness

The [benchmarks](benchmarks.md) show jScratch well ahead of scratch-vm on compute-heavy projects but behind TurboWarp on most of them. Running on the JVM is not enough by itself: TurboWarp's code also gets compiled to machine code, by V8. The items below are where the benchmarks and the generated bytecode point.

They come before the extensions and the major goals further down because those build on them: functions, local variables and calls into Java all need values with known types, and macros make scripts bigger. The goal is to get within two to three times TurboWarp on the compute benchmarks, not to match it exactly. jScratch is already far ahead of scratch-vm, and past that point the features are worth more than the last few milliseconds.

- [x] **Benchmarks.** CPU-heavy projects timed against scratch-vm and TurboWarp, with the output of every engine checked against the expected result. They run on every push to `main`.
- [x] **Cheap yields between frames.** Every loop iteration outside "run without screen refresh" used to hand control from the scheduler thread to the script's virtual thread and back through two semaphores. That cost about 5 microseconds, while a yield costs about 45 nanoseconds in TurboWarp and 150 in scratch-vm, which made the `loops` benchmark about 120 times slower than TurboWarp. Scripts stay on virtual threads: the yielding script now asks the scheduler which script comes next and hands control straight to it, and when it is the only active script, which it is in most frames, the yield returns without any thread switch. The scheduler runs on a virtual thread too. This settled how loops and waits compile, so the items below build on it. Resumable state machines, the way TurboWarp uses generators, remain the way to run scripts where there are no virtual threads, like the [in-page preview](#playground).
- [x] **Cheaper yield checks in warp loops.** Inside "run without screen refresh", every loop iteration used to read the clock and the script's volatile stop flag to enforce the 500 ms limit. Now a run of up to 256 iterations shares one look, and the run only grows while the looks stay under a millisecond apart, so a loop with a slow body still looks every time. That made `sort` 2.5 times faster and `sieve` 2.3 times faster. Dropping the check entirely, as TurboWarp does outside the editor, measured no faster, so the limit stays and a "run without screen refresh" block that never ends still lets the project draw twice a second, as it does in Scratch.
- [x] **Split large scripts.** Break scripts into several methods well before the JVM's 64 KiB method limit, so a long chain of blocks never keeps a project from compiling. Aim for methods under 8000 bytes of bytecode: HotSpot never compiles anything larger to machine code, so a big script would stay interpreted forever. This has to happen before macros, which expand blocks in place and make scripts bigger. Done for scripts and custom blocks, which spill long chains into helper methods under an estimated size budget. Splitting happens between blocks, so a single block with an enormous tree of reporters still compiles into one method, and the run-once members (constructors, `lookupVariable` and the monitor tables) still grow with the project; both would need the same treatment at roughly ten times the sizes real projects reach today.
- [ ] **Compatibility corpus.** A set of real projects compiled and run headless on every build, with screenshots compared against reference frames. It comes before the type work below because changing how values are stored is where Scratch's casting rules are easiest to break: empty strings compared with 0, numbers with spaces around them, `NaN`, `Infinity`, negative zero and hexadecimal strings. The benchmarks only check one result per project and would miss most of that.
- [ ] **Better type inference.** Track variables that only ever hold numbers so they can live as primitive doubles instead of boxed objects. Today every `set` and `change` allocates a `Double`.
- [ ] **Typed comparisons.** Comparing a variable with a number literal boxes the literal and goes through the general `Cast.compare(Object, Object)`. Emit a numeric comparison when one side is known to be a number and the other is a number at run time.
- [ ] **Turbo mode and frame rate.** Command line options and system properties for turbo mode and a custom frame rate, like TurboWarp offers.
- [ ] **Pluggable renderers.** A renderer interface in the runtime, so drawing can move to the GPU without growing every compiled JAR, and so others can write renderers for Metal, OpenGL or anything else. Renderers only draw: collision, color sensing and the pen layer stay on the CPU, so a project behaves the same whichever renderer runs it. The interface stays internal until a second renderer exists, since one designed around Java2D alone will need to change. It is also a first step toward the embeddable runtime and the [in-page preview](#playground) further down. It comes before the effects and pen items below so that work lands in the Java2D renderer once instead of being written and then moved, and before the extensions, because the runtime is small today and every extension that adds platform code makes the split more expensive.
    - [ ] **Java2D renderer.** Move today's drawing behind the interface. Costumes are uploaded once, and each frame sends the costume, transform, ghost and effects of every sprite, so a renderer can apply effects itself. It stays built into every JAR as the fallback and is the default in headless mode and for screenshots, so their output is deterministic.
    - [ ] **WebGPU renderer (only if the benchmarks call for it).** Java2D already draws sprites with hardware acceleration on every desktop platform, so a GPU renderer would only win where Java2D falls back to the CPU: mostly graphic effects, which it could apply in shaders. Build it only if the rendering benchmarks still show a large gap with TurboWarp after the faster effects and pen items below. It would be a plugin built on [jWebGPU](https://github.com/xpenatan/jWebGPU), which runs on Metal, Vulkan, DirectX 12 and OpenGL through wgpu or Dawn. It has to draw straight into the window: rendering offscreen and copying each frame into Swing would read every frame back from the GPU only for Java2D to upload it again, which is likely slower than Java2D alone. Say bubbles and vector costumes are still rasterized on the CPU and uploaded as textures, as scratch-render does.
    - [ ] **Choosing a renderer.** Renderers are found with `ServiceLoader`, inside the compiled JAR or in a plugin JAR next to it. Each one checks whether it can start, `-Djscratch.renderer=<name>` picks one explicitly, and a renderer that fails to start falls back to Java2D.
    - [ ] **`--gpu` option.** The CLI embeds the WebGPU renderer only when asked. Its native libraries add 3 to 4 MB per platform on top of the runtime's 3 MB, so `--gpu` embeds every desktop platform and `--gpu=mac-arm64,windows-x64` picks a few.
- [ ] **Rendering benchmarks.** The benchmarks skip drawing today. Add projects heavy on clones, pen, stamping and graphic effects on large sprites, and compare them with TurboWarp's WebGL renderer. They decide whether the items below are worth doing and whether the WebGPU renderer above gets built at all.
- [ ] **Faster graphic effects.** Effects are computed for every pixel of the costume on one thread, again every time a value changes, so a large costume drawn small still pays for every pixel at full resolution. Compute them only for the stage pixels the sprite covers, split the work across cores, and cache color and brightness per distinct color. Each changed effect also produces a new image that Java2D has to upload to the GPU again, so fewer pixels means smaller uploads too.
- [ ] **Smaller pen uploads.** The pen layer is a 960 x 720 image drawn on the CPU, and on every frame the pen touched, Java2D uploads all of it to the GPU again. Keep a copy in video memory and copy only the area that changed into it.

## Extensions

- [ ] **Makey Makey.** Its hats map onto key presses, so it is cheap to add.
- [ ] **Music.** Instruments and drums through `javax.sound.midi`, which ships with the JDK.
- [ ] **Text to Speech and Translate.** These depend on online services. They will only be added if there is a way to do it without sending project data somewhere the user did not expect.
- [ ] **Custom extensions in JavaScript.** Load the same extension files TurboWarp does, so the existing community extensions keep working. The runtime would run them in a bundled JavaScript engine and provide the `Scratch` object they expect: `Scratch.extensions.register`, the block and argument types, and the parts of `Scratch.vm` that extensions commonly reach into. Extensions that depend on the browser, such as ones that draw on a canvas or open web pages, will need replacements or will not work.
- Video Sensing and hardware extensions are out of scope for now.

## Cloud variables

Cloud variables behave as ordinary variables today, so their values are lost when the project stops.

- [ ] **Saved values.** Store cloud variables in a file next to the project so they survive a restart, which covers high scores and save data in single-player projects.
- [ ] **Cloud servers.** Connect to a server that speaks Scratch's cloud protocol, such as TurboWarp's cloud server, through the JDK's WebSocket client. The server is chosen with a command line option or a system property and is off by default, so a project never goes online unless the person running it asks for that.

## Playground

- [ ] **Faster compiles.** Cache the unpacked runtime JAR between compiles instead of re-zipping it every time.
- [ ] **Load by project ID.** Paste a Scratch project link instead of downloading the `.sb3` first.
- [ ] **Clearer output.** Show warnings next to the block that caused them and group the bytecode listing by sprite.
- [ ] **Run projects in the page.** A preview that runs the compiled classes in the browser, to show that a project works without downloading the JAR. The page cannot load new JVM classes, so a small bytecode interpreter compiled with TeaVM would run them against a browser build of the runtime: a canvas in place of Java2D and Swing, the browser's own SVG rendering in place of JSVG, Web Audio in place of the sound decoders, and TeaVM threads in place of virtual threads. That means splitting the runtime into a shared core and a backend per platform first. See [Web playground](web-playground.md#running-projects-in-the-page).

## Distribution

- [ ] **Release builds.** Publish the CLI JAR on GitHub Releases for every tagged version.
- [ ] **Native launchers.** An option to package a compiled project with `jpackage`, so players do not need a Java install.
- [ ] **Gradle plugin.** Compile `.sb3` files as part of another project's build.

## Later: major goals

These are bigger projects that build on everything above. They will take a while, and their shape will change as the earlier work settles.

### Two-way interop with the JVM

Compiled projects are already JVM classes, so the goal is to let them work with Java, Kotlin and other JVM languages in both directions.

- [ ] **Calling Java from Scratch.** Extension blocks that call into JVM libraries, with the compiler emitting direct method calls instead of going through a lookup at run time.
- [ ] **Calling Scratch from Java.** Use a compiled project as a library: start it, send broadcasts, read and set variables and lists, and listen for events from ordinary JVM code.
- [ ] **Library extensions.** Packages of blocks that wrap a specific library with an interface that feels like Scratch, instead of exposing its raw API. Each extension describes its blocks and how they compile.
- [ ] **Embeddable runtime.** Let the host decide how the project runs: its own tick in place of the 30 fps scheduler, its own drawing surface in place of the Swing window, or no stage at all.

With these in place, a project could become a Minecraft mod through blocks that bind to Fabric, or a desktop app with a JavaFX interface.

### Advanced language features

Scratch is easy to start with, but larger projects outgrow it: custom blocks cannot return values, there are no local variables, and clones are the only way to have more than one of something. The goal is a richer language on top of Scratch that stays a strict superset of it. Every Scratch project must compile and behave exactly as it does today, and the new features only come into play when a project uses them. [Language features](language-features.md) has mockups of what the blocks could look like.

- [ ] **Functions.** Custom blocks that report a value, local variables scoped to a script or a custom block, and recursion that does not need a list as a manual stack.
- [ ] **Macros.** Blocks that expand into other blocks at compile time, so repeated patterns can be written once without the cost of a call at run time.
- [ ] **Objects.** Classes with their own fields and methods, and instances that can be created, passed around and stored in variables and lists. Sprites and clones keep working as they do now, and could later be described as classes themselves.

### Desktop IDE

- [ ] **A full desktop editor.** Edit blocks, costumes and sounds, then compile and run the project in one click without leaving the editor.
- [ ] **Debugging.** Breakpoints on blocks, stepping through scripts, and a live view of variables, lists and running scripts.
- [ ] **Extension support.** Browse and add library extensions, and see their blocks in the palette like any built-in category.

### Older Scratch versions and derivatives

Most of this will probably go into separate related projects instead of jScratch itself, reusing parts of jScratch where that makes sense. It is listed here because there is no other place to track it yet.

- [x] **A converter for Scratch 1.x and 2.x.** Turn `.sb` and `.sb2` projects into `.sb3` with the Scratch Foundation's own code (scratch-sb1-converter and scratch-vm's importer and exporter), so they compile like any other project, in the CLI, in the playground and straight from the Scratch website. See [Getting started](getting-started.md#scratch-14-and-scratch-2-projects).
- [ ] **Reviving Scratch 1.x and 2.x.** Converting a project gets it running, but not the way it ran back then. The bigger goal is to bring the old versions themselves back on a modern platform, the JVM, with their own look and behavior. 1.x was built on Squeak Smalltalk and 2.0 on Flash, and those platforms have not aged well, but the versions themselves deserve better than to be left to rot. Many people feel they were better than what came after, and many more have strong nostalgia for them.
- [ ] **Snap*!* and other derivatives.** Snap*!* has its own XML project format and features Scratch lacks, like first-class procedures and continuations, so it needs its own front end and much of its own runtime. Derivatives based on Scratch 1.x and 2.x fall in the same group and would build on the revival work above.

## Have a request?

Open an issue on [GitHub](https://github.com/AstroBlocksMod/jScratch/issues) with the project that fails, or the block you need. A project that reproduces the problem moves an item up the list faster than anything else.
